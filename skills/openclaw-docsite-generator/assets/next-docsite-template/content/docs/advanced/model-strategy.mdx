## Decision Table

| Task type | Recommended model family | Why it fits |
| --- | --- | --- |
| Coding tasks | Claude, GPT, Qwen coder | Strong code generation, editing, and repo reasoning |
| Web research | GPT, Claude, Grok | Good synthesis across broad information sources |
| Deep reasoning | Claude and advanced GPT tiers | Better at long-horizon planning and nuanced tradeoffs |
| Automation tasks | Qwen or smaller task-focused models | Lower cost for repetitive operational work |
| Context processing | Local models | Good fit for private or high-volume summarization pipelines |

The goal is not to memorize brand names. The goal is to match capability to workload while keeping latency and spend visible.

## Routing Heuristics

Use simple routing rules before building a complex planner:

- If the task writes or edits code, start with a coding-oriented model profile.
- If the task reads many documents, optimize for long-context or summarization strength.
- If the task repeats on a schedule, favor the smallest model that meets the quality bar.
- If the data cannot leave your boundary, route to approved local or private infrastructure.

## Starter Policy Example

```yaml
routes:
  - when: task_type == "coding"
    use: coder-primary
  - when: task_type == "research"
    use: research-primary
  - when: task_type == "automation"
    use: low-cost-runner
  - when: task_type == "private-indexing"
    use: local-context-model
fallback: reasoning-default
```

## What To Measure

Track these before adding more models:

- task success rate
- median latency
- average token spend
- human rewrite rate
- failure rate by task type

## Anti-Patterns

- One premium model for every workflow.
- Adding new providers before measuring the current routing policy.
- Routing based on model popularity instead of workload evidence.
