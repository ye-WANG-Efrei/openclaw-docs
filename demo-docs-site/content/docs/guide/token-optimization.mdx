Many people who use OpenClaw for a while find that their API bills are higher than expected. In this chapter we will clarify exactly **where tokens are being spent, and how to bring those costs down systematically.**

The core insight up front: the main source of token cost is not the one question you just asked — it is **the large amount of context that gets carried along with every single conversation turn.** Once you understand this, the optimization approach becomes clear.

---

## 1. Understanding Where Token Costs Come From

In OpenClaw, every model call sends the following content to the model:

1. **System Prompt**
2. **Workspace files** (AGENTS.md, SOUL.md, etc.)
3. **Conversation history**
4. **Tool execution results**
5. **The current user question**

All five of these are bundled together and sent to the model. So even if you asked a very short question, the actual tokens consumed can be quite large.

> **Core insight: Token costs are driven primarily not by "the current question" but by the large amount of context that gets repeatedly carried along.**

Therefore, optimization falls into three directions:

- **Reduce unnecessary context injection**
- **Control the frequency of automatic turns**
- **Choose models and billing methods wisely**

---

## 2. Four Core Optimization Methods

### Method 1: Use QMD to Inject Knowledge Precisely

**What is the problem?**

If your Agent is connected to a large knowledge base, the default behavior is often to push the entire library into the context. This is extremely wasteful.

**QMD's approach: retrieve first, then inject.**

The core of QMD (Query Matched Documents) is:

> Instead of having the model read the entire knowledge base, first find the most relevant passages locally, then inject only those passages into the model.

**Workflow:**

1. Scan the local Markdown document library
2. Segment the documents
3. Build a vector index
4. Write the vectors into a vector database
5. Compute similarity when the user asks a question
6. Return only the most relevant passages to inject into the model

**Configurable parameters:**

| Parameter | Purpose |
| --- | --- |
| Maximum Result | Controls the number of passages returned |
| Maximum Snippet Chars | Controls the maximum length of a single passage |
| Maximum Injected Chars | Controls the total character cap injected into the model |

**Best for:** Large knowledge bases, documentation-driven projects, notes library queries.

> Remember this: the problem is not "the model isn't smart enough" — it is "the context being provided is wrong." Wrong context, even with a stronger model, only makes the system more expensive, not necessarily more accurate.

---

### Method 2: Run Heartbeat with a Local Small Model

**What is Heartbeat?**

Heartbeat is OpenClaw's scheduled wake-up mechanism, used for:

- Advancing long-running tasks
- Checking task status
- Triggering automated processes

**What is the problem?**

Every Heartbeat produces one complete Agent turn. Even if the output is short, the input context can still be very long.

Let's do the math:

- Heartbeat fires every 30 minutes
- That is approximately **1,444 calls per month**
- If all of those use a cloud-based large model, costs accumulate continuously

**Solution: Delegate Heartbeat to a local small model.**

It is recommended to use [Ollama](https://ollama.com) to run a small model locally for Heartbeat tasks, completely avoiding the fees generated by high-frequency cloud model calls.

**Principle: Heartbeat is only responsible for triggering, reminding, and inspection. Complex reasoning tasks remain with the primary model.**

---

### Method 3: Prefer Subscription Billing

AI services typically come in two billing modes:

| Mode | Characteristics | Best for |
| --- | --- | --- |
| **Pay-per-use API** | Pay for what you use, flexible | Low-frequency use, testing phase |
| **Subscription** | Fixed monthly fee, more economical for heavy use | High-frequency call scenarios |

A real comparison:

- Minimax API pay-per-use: approximately **$30 / day**
- Some cutting-edge model APIs: approximately **$500 / day**

With heavy use, API costs can spiral out of control quickly. Where the vendor permits, **prefer subscription billing.**

---

### Method 4: Generate a Cost Health Report to Locate Waste

Many token expenditures are not necessary — they come from:

- Poorly designed workflows
- Unnecessary context repetition
- High-frequency polling instead of event-driven triggers

**Recommended practice: regularly generate an OpenClaw cost health report.**

A report should include:

- Token consumption breakdown per task
- Model call frequency
- Proportion analysis of each cost type

Then optimize from the largest cost downward.

**A typical optimizable case:**

> Polling every 10 minutes to check "whether a certain event has occurred."

If this is replaced with an **event-triggered mechanism** — only calling the model when the event actually occurs — the number of model calls can be reduced by more than 90%.

## 3. Key Practical Principles

Having covered the four methods, keep these four principles in mind to complete the optimization:

1. **Reduce context volume first** — context is the biggest cost driver
2. **Reduce high-frequency automatic turns** — Heartbeat frequency should match task value
3. **Layer models appropriately** — not everything needs the most expensive model
4. **Continuously analyze costs** — cost structure changes with usage patterns; review regularly

**Recommended model layering architecture:**

| Tier | Responsibility | Recommendation |
| --- | --- | --- |
| Large model | Core reasoning, complex tasks | Claude / GPT-4o, etc. |
| Small model | Supporting tasks, Heartbeat | Local Ollama models |
| Local retrieval | Knowledge injection | QMD vector retrieval |

## 4. Engineering Practice Recommendations

With the theory covered, here are actionable recommendations you can implement right away.

### 1. Establish a Cost Baseline

Before optimizing, record your current state — otherwise you won't know whether optimization is working:

- Average input token count
- Model call frequency
- Model types used
- Daily cost estimate

### 2. Compare Before and After Enabling QMD

Before and after enabling QMD, compare these metrics:

- Number of passages matched
- Total characters injected
- Answer quality (manual evaluation)
- Task completion rate

### 3. Control the Scope of Heartbeat's Responsibilities

Heartbeat should only be responsible for:

- **Reminding**: notifying the primary model that a task is pending
- **Triggering**: starting downstream processes
- **Inspection**: checking whether any status is abnormal

Avoid executing complex logic in a Heartbeat turn — that is burning money.

### 4. Prioritize Optimizing These Two Problem Types

Based on experience, costs drop fastest when you fix these two:

- **Light tasks carrying large context**: a simple query that is unnecessarily loaded with the entire knowledge base
- **Fixed-interval polling**: a timer replacing event triggers, wasting a model call every time

---

## 5. Summary

Token cost optimization in OpenClaw is fundamentally a **system architecture optimization problem**, not simply "switching to a cheaper model."

Core strategy summary:

- **Control context injection**: use QMD for precise retrieval, avoid full-library injection
- **Reduce automatic turn frequency**: use local small models for Heartbeat, reduce cloud calls
- **Optimize billing methods**: prefer subscription billing for high-frequency scenarios
- **Regularly analyze cost structure**: find the most wasteful points and start there

Through these methods, you can significantly reduce running costs while maintaining full Agent capabilities.
