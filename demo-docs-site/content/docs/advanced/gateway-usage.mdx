## Why Add A Gateway

A gateway gives OpenClaw one controlled surface for model traffic instead of scattering provider logic across multiple apps and services. That makes it easier to enforce policy, track spend, and add routing logic over time.

## Common Gateway Responsibilities

| Responsibility | Why it matters |
| --- | --- |
| model routing | choose providers or model tiers centrally |
| policy enforcement | block unsafe or disallowed workloads |
| cost control | meter and cap expensive routes |
| audit logging | explain which model was used and why |
| retries and fallbacks | reduce user-facing failure rates |

## Reference Topology

```text
Client -> OpenClaw app -> Gateway -> Provider API or local model runtime
```

## Starter Config Pattern

```env
OPENCLAW_GATEWAY_URL=https://gateway.example.com
OPENCLAW_GATEWAY_TOKEN=<service-token>
OPENCLAW_GATEWAY_TIMEOUT_MS=30000
```

## Operational Checks

- log the final provider and model after routing
- expose request ids for tracing
- separate dev and prod gateway credentials
- record fallback behavior when a provider fails

## Common Mistakes

- hiding routing rules inside application code instead of the gateway layer
- failing open when the gateway cannot decide safely
- using one gateway token across every environment and service
