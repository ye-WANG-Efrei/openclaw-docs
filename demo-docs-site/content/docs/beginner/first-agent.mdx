## The Goal Of The First Agent

The first agent should be useful enough to test the whole pipeline but small enough to understand in one sitting. A repository helper or documentation assistant is usually a better first target than a large autonomous workflow.

## Starter Agent Shape

Use this as a conceptual starter spec and adapt the field names to the real OpenClaw schema:

```yaml
name: repo-helper
goal: Answer repository questions and propose safe implementation steps.
model_profile: reasoning-default
tools:
  - filesystem
  - terminal
skills:
  - openclaw-docsite-generator
memory:
  mode: session
  persist_summary: true
```

The important part is not the exact field names. The important part is that the first agent already makes explicit decisions about model profile, tool scope, skills, and memory.

## Build It In Four Decisions

1. Define a narrow outcome.
   Example: summarize the current repository and suggest next steps.
2. Choose one model profile.
   Start with a balanced default before adding routing.
3. Restrict tools.
   Only allow the tools that are necessary for the first workflow.
4. Attach one skill.
   Use a concrete skill so the agent has procedural guidance, not only general reasoning.

## What A Successful Run Looks Like

A successful first run should show all of these:

- the agent receives a clear task
- the selected model is visible in logs or traces
- the skill is loaded when relevant
- the tool calls are understandable and limited
- the output is useful without manual repair

## Example Validation Prompt

```text
Summarize this workspace, identify the main project goal, and propose the next three implementation tasks.
```

## Common Mistakes

- Starting with a fully autonomous agent before you have a safe tool boundary.
- Letting the first agent choose from too many models without a routing policy.
- Treating the first successful answer as enough validation without checking logs and permissions.
