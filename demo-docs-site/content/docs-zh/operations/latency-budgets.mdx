## 原则

延迟预算不是一张写给看板的数字表，而是帮助团队在“体验、成本、模型能力”之间做权衡的工程边界。只要某类工作流没有明确的延迟预算，系统就很容易在最忙的时候变慢、变贵，还没有清晰的降级策略。

## 什么时候应该定义延迟预算

特别适合这些场景：

- 面向终端用户的同步交互
- 需要多步模型调用的复杂任务
- 同时存在“高质量路径”和“快速路径”的系统
- 对 Gateway 回退时间敏感的工作流

## 实施模式

1. 先按工作流分级，例如交互式、后台异步、批处理
2. 为每一类定义目标延迟和最大可接受延迟
3. 根据预算调整模型档位、上下文大小和回退策略
4. 用真实观测数据持续校准预算

## 反模式

- 给所有工作流设同一个延迟目标
- 只看平均延迟，不看尾延迟
- 预算超标后没有明确降级动作

## 检查清单

- 是否知道每类任务的目标响应时间？
- 超预算时系统会优先牺牲什么？
- 路由规则是否考虑了延迟预算？
- 看板中是否能区分平均延迟和 P95/P99？
