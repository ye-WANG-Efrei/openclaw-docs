## 为什么要专门做 Gateway 可观测性

一旦模型流量统一经过 Gateway，很多关键问题都会集中在这里暴露：某个提供方是否失败、某类任务是不是总命中高成本模型、某条回退策略是否被频繁触发。没有 Gateway 可观测性，团队只能看到“用户反馈变差”，却看不到具体哪一层出了问题。

## 应该记录的核心信号

- 请求量与成功率
- 每个路由规则的命中次数
- 最终落到的提供方与模型
- 重试与回退的触发次数
- 平均延迟与尾延迟
- token 成本趋势

## 一个实用的仪表盘视角

| 维度 | 要回答的问题 |
| --- | --- |
| 提供方 | 是哪家在出错或变慢？ |
| 模型 | 哪个模型最贵、最慢或最不稳定？ |
| 工作流 | 哪类任务最容易触发回退？ |
| 环境 | 问题只出现在 staging 还是 production？ |

## 实践建议

1. 给每次请求分配请求 ID
2. 记录路由前后的模型选择
3. 单独统计回退链路
4. 把成本和延迟一起看，而不是分开看

## 常见误区

- 只记录最终模型，不记录路由决策过程
- 有错误日志，但没有按任务类型分层
- 成本分析脱离了请求上下文
