很多人在使用 OpenClaw 一段时间后，会发现 API 账单比预期高出不少。这个章节我们就来搞清楚：**Token 到底花在哪了，以及怎么系统性地把它降下来。**

核心结论先说：Token 成本的主要来源，不是你问的那一个问题，而是**每次对话都在重复携带的大量上下文**。搞懂这一点，优化思路就清晰了。

---

## 一、理解 Token 成本的来源

在 OpenClaw 中，每一轮模型调用，实际发送给模型的内容包括：

1. **System Prompt（系统提示）**
2. **Workspace 文件**（AGENTS.md、SOUL.md 等）
3. **对话历史**
4. **工具执行结果**
5. **当前用户问题**

这五类内容会被一起打包发给模型。所以即使你只问了一句很短的问题，实际消耗的 Token 也可能非常多。

> **核心结论：Token 成本的主要驱动不是"当前问题"，而是重复携带的大量上下文。**

因此，优化的方向有三个：

- **减少不必要的上下文注入**
- **控制自动回合的频率**
- **合理选择模型与计费方式**

---

## 二、四种核心优化方法

### 方法一：用 QMD 精准注入知识片段

**问题是什么？**

如果你的 Agent 连接了一个大型知识库，默认行为往往是把整个库的内容都塞进上下文。这非常浪费。

**QMD 的思路：先检索，再注入。**

QMD（Query Matched Documents）的核心是：

> 不让模型读整个知识库，而是先在本地找到最相关的片段，只把这些片段注入给模型。

**工作流程：**

1. 扫描本地 Markdown 文档库
2. 对文档进行分段
3. 建立向量索引
4. 将向量写入向量数据库
5. 用户提问时计算相似度
6. 只返回最相关的片段注入模型

**可调参数：**

| 参数 | 作用 |
| --- | --- |
| Maximum Result | 控制返回的片段数量 |
| Maximum Snippet Chars | 控制单个片段的最大长度 |
| Maximum Injected Chars | 控制注入模型的总字符上限 |

**适用场景：** 大型知识库、文档型项目、笔记库查询。

> 记住这句话：问题不是"模型不够聪明"，而是"拿到的上下文不对"。错误的上下文即使给更强的模型，也只会让系统更贵，不一定更准。

---

### 方法二：用本地小模型运行 Heartbeat

**Heartbeat 是什么？**

Heartbeat 是 OpenClaw 的定时唤醒机制，用于：

- 推进长期任务
- 检查任务状态
- 触发自动流程

**问题在哪里？**

每次 Heartbeat 都会产生一次完整的 Agent 回合。即使输出很短，输入的上下文依然可能很长。

我们算一笔账：

- 每 30 分钟执行一次 Heartbeat
- 每月约 **1,444 次调用**
- 如果全部用云端大模型，成本会持续累积

**解决方法：把 Heartbeat 交给本地小模型。**

推荐使用 [Ollama](https://ollama.com) 在本地运行小模型来承担 Heartbeat 任务，完全避免高频调用云模型产生的费用。

**原则：Heartbeat 只负责触发、提醒、巡检。复杂推理任务仍交给主模型完成。**

---

### 方法三：优先使用订阅计费

AI 服务通常有两种收费模式：

| 模式 | 特点 | 适合场景 |
| --- | --- | --- |
| **API 按量计费** | 用多少付多少，灵活 | 低频、测试阶段 |
| **订阅制** | 固定月费，高频使用更划算 | 高频调用场景 |

一个真实的对比数据：

- Minimax API 按量计费：约 **30 美元 / 天**
- 部分最新模型 API：约 **500 美元 / 天**

在高频使用的情况下，API 成本可能迅速失控。在厂商允许的前提下，**优先考虑订阅制**。

---

### 方法四：生成成本体检报告，定位浪费来源

很多 Token 消耗并非必要，而是来自：

- 不合理的流程设计
- 不必要的上下文重复
- 高频轮询替代了事件触发

**推荐做法：定期生成 OpenClaw 成本体检报告。**

报告应包含：

- 每个任务的 Token 消耗明细
- 模型调用频率
- 各类消耗的占比分析

然后从高到低逐项优化。

**一个典型的可优化案例：**

> 每 10 分钟轮询一次"某个事件是否发生"。

如果改为**事件触发机制**——只在事件真正发生时才调用模型——模型调用次数可以减少 90% 以上。

## 三、关键实践原则

掌握了四种方法，再记住这四条原则，优化才能做到位：

1. **优先减少上下文体积** — 上下文是最大的成本来源
2. **减少高频自动回合** — Heartbeat 频率要和任务价值匹配
3. **合理分层模型** — 不是每件事都需要最贵的模型
4. **持续进行成本分析** — 成本结构会随使用方式变化，定期复查

**推荐的模型分层架构：**

| 层级 | 职责 | 推荐 |
| --- | --- | --- |
| 大模型 | 核心推理、复杂任务 | Claude / GPT-4o 等 |
| 小模型 | 辅助任务、Heartbeat | 本地 Ollama 模型 |
| 本地检索 | 知识注入 | QMD 向量检索 |

## 四、工程实践建议

理论讲完了，下面是可以直接落地的操作建议。

### 1. 建立成本基线

在优化之前，先把当前状态记录下来，否则你不知道优化是否有效：

- 输入 Token 平均值
- 模型调用频率
- 所用模型类型
- 日成本估算

### 2. 上线 QMD 后进行对比

QMD 上线前后，对比这些指标：

- 命中片段数量
- 总注入字符数
- 回答质量（人工评估）
- 任务完成率

### 3. 控制 Heartbeat 的作用边界

Heartbeat 应该只负责：

- **提醒**：告知主模型有任务待处理
- **触发**：启动后续流程
- **巡检**：检查状态是否异常

避免在 Heartbeat 回合里执行复杂逻辑，那是在烧钱。

### 4. 优先优化这两类问题

经验来看，以下两类问题成本下降最快：

- **轻任务带大上下文**：明明只是一个简单查询，却携带了整个知识库
- **固定时间轮询**：用定时器代替了事件触发，每次都白白消耗一次模型调用

---

## 五、总结

OpenClaw 的 Token 成本优化，本质上是一个**系统架构优化问题**，而不只是"换个便宜模型"那么简单。

核心策略总结：

- **控制上下文注入**：用 QMD 精准检索，不做全库注入
- **降低自动回合频率**：Heartbeat 用本地小模型，减少云端调用
- **优化计费方式**：高频场景优先订阅制
- **定期分析成本结构**：找到最浪费的环节，从那里开始优化

通过这些方法，可以在保持 Agent 能力的同时，显著降低运行成本。
