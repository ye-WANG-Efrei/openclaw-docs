## 这章要回答什么

很多人学习 AI 的第一步，是学会怎么写 prompt。再往后一点，会开始理解 `context engineering`，也就是如何给模型准备足够好的上下文、资料和约束。

但当 AI 的角色从“回答你一个问题”，变成“持续替你完成任务”时，仅仅会写 prompt，或者会塞上下文，已经不够了。

这时候真正重要的新概念是：`harness engineering`。

它要解决的问题不是“这一句 prompt 写得够不够好”，而是：

- AI 在什么环境里工作
- 它能调用哪些工具
- 它做完之后如何判断结果是否合格
- 它如何记录过程，避免长任务中途失忆
- 哪些节点必须人工介入，哪些可以自动放行

如果说 `prompt engineering` 关注的是“你怎么对 AI 说话”，`context engineering` 关注的是“你给 AI 什么资料”，那么 `harness engineering` 关注的就是：**你如何搭建一整套可运行的工作系统，让 AI 能稳定地干活。**

## 从 Prompt 到 Context，再到 Harness

我们可以把这三个概念看成 AI 使用方式的三次升级。

| 阶段 | 核心问题 | 关注重点 | 适合的任务形态 |
|---|---|---|---|
| `prompt engineering` | 我该怎么提问？ | 指令表达是否清晰 | 单轮问答、改写、总结 |
| `context engineering` | 我该给模型什么资料？ | 上下文组织、资料选择、约束补充 | 长文总结、资料分析、代码阅读 |
| `harness engineering` | 我怎样让 AI 稳定执行任务？ | 环境、工具、标准、记录、流程控制 | Agent、自动化、多步骤工作流 |

这不是说前面的概念过时了，而是说：**任务越复杂，你越要从“写一句好 prompt”升级到“搭一套能运转的系统”。**

## 为什么 Prompt 已经不够了

在简单任务里，一个 prompt 往往已经够用。

比如：

- 帮我总结这篇文章
- 帮我翻译这一段内容
- 帮我改一封邮件

但一旦任务变成这样：

- 阅读多个来源，产出研究报告
- 遍历代码仓库，修改文件并运行验证
- 把一次录音变成转写、摘要、播客文案和发布素材
- 让多个 agent 分工合作，持续完成一个项目

问题就变了。

这时候模型不只是“答一句话”，而是在一个更长的任务链里不断做判断。它会遇到很多 prompt 本身解决不了的问题：

- 文件太多，不知道去哪里找资料
- 工具太多，不知道什么时候调用哪个
- 任务太长，上下文越来越重，开始变慢、变笨
- 没有明确标准，不知道结果是否合格
- 没有过程记录，中途一旦丢上下文，任务就断了

所以我们真正要做的，不只是继续雕 prompt，而是搭建一个让 AI 能够持续工作的“轨道系统”。这就是 `harness engineering` 的价值。

## 什么是 Harness Engineering

`Harness` 这个词，你可以把它理解成“驾驭系统”或“工作框架”。

它的核心思想很简单：

> 不要只要求 AI 给你一个答案，而要为 AI 提供一套环境，让它可以在这个环境里持续完成任务。

这套环境通常至少包含四个部分。

### 1. 清晰的工作环境

AI 不是靠“感觉”工作的，它高度依赖环境结构。

如果你的目录混乱、文件命名随意、资料入口不明确，AI 就会不断把注意力浪费在“我应该读哪个文件”“这个资料是不是最新版”上。

所以，好的 harness 第一步就是让环境清晰：

- 文件命名规范
- 目录层级可预测
- 输入和输出路径明确
- 关键资料有固定位置
- 每类任务有固定的产物命名规则

这听起来像工程卫生，但其实它直接决定了 AI 是否能稳定执行任务。

### 2. 可复用的工具和 Skills

如果每次都让 AI 从零开始想办法完成任务，它就会很不稳定。

更好的方式是给它现成的工具和工作流模块。例如：

- 转写工具
- 深度研究工具
- 评审工具
- 报告转 `PPT` 的流程
- 报告转 `PDF` 的流程
- 代码修改与验证脚本
- 可复用的 `skills`

这一步非常关键。因为当 AI 可以调用现成工具时，它做的就不再是“临场发挥”，而是“在稳定框架中执行”。

这也是为什么像 `Codex`，`Claude Code` 这样的系统很重要。它的意义不只是“能写代码”，而是它让 AI 进入了一个真实工作环境：

- 能看文件
- 能修改文件
- 能运行命令
- 能分步验证结果

这已经不是普通聊天，而是工程系统里的任务执行。

### 3. 明确的验收标准

很多人让 AI 做事时，最容易忽略的一点是：**AI 必须知道什么叫做“标准”。**

没有标准，AI 就无法自我校准。

比如做研究任务时，你可以明确要求：

- 只看最近 `3` 个月或 `6` 个月资料
- 信息源必须是一手来源
- 不接受转载整合站
- 至少需要 `2` 个以上 source 交叉验证
- 输出必须包含结论、证据、风险和下一步建议

有了这些标准，AI 才能在执行后做自查，而不是每一步都等你重新判断。

所以从 `human in the loop` 迈向 `agentic`，并不是把人完全拿掉，而是把人的角色从“每一步盯着看”变成“在关键验收节点介入”。

### 4. 过程记录与长任务管理

很多人以为上下文越长越好，其实不是。

长上下文确实能带来更多信息，但任务一旦变复杂，模型就可能在中后段出现明显退化：

- 变慢
- 变笨
- 遗漏之前说过的要求
- 忘记任务当前阶段
- 输出开始飘

所以复杂任务不能只靠堆上下文，还需要外部记录机制。

例如：

- 用文档记录任务步骤
- 用状态文件记录当前进展
- 用日志记录关键决策
- 把阶段性产物落盘，而不是只存在对话里

这样做的好处是，AI 即使中途切换模型、重启会话或跨多个 agent 协作，也能靠记录继续往前走。

## Codex、Skills、多 Agent 为什么都和它有关

很多人第一次听到 `harness engineering`，会觉得这是一个抽象概念。但只要你看真实系统，就会发现它其实已经非常具体。

### Codex & Claude Code

`Codex` & `Claude Code`代表的是一种“让 AI 在真实工作环境里行动”的模式。

它不只是生成代码，而是能在一个仓库里：

- 读取上下文
- 修改文件
- 调用工具
- 执行命令
- 做验证和迭代

这本质上就是 harness 的体现。你不是只给它一个 prompt，而是给它一个可操作的环境。

### Skills

`skills` 的意义，是把重复任务模块化。

如果你经常需要：

- 视频转写后做知识提炼
- 文档做结构化整理
- PR 做评审
- 研究内容做标准化输出

那么最稳的方式不是每次重新描述一遍，而是沉淀成 skill。

Skill 的本质就是 harness 中的“稳定工具能力”。

### 多 Agent

多 agent 不是多开几个模型窗口那么简单。

真正有效的多 agent，背后一定有分工规则：

- 谁负责检索
- 谁负责产出
- 谁负责校验
- 谁负责汇总
- 失败时怎么回退

如果没有这些边界，多 agent 只会放大混乱，不会放大效率。

所以多 agent 的上限，不取决于你开了多少 agent，而取决于 harness 是否清晰。

## Human in the Loop是设计问题

很多人一听到 `agentic`，就会以为目标是“彻底不要人”。

其实更现实的理解是：

- 低风险、重复性的步骤，让 AI 自动做
- 高风险、强判断性的步骤，让人介入

这才是更成熟的系统设计。

所以 `human in the loop` 不是失败，而是一个必须被设计进去的机制。

重点不是“有没有人工”，而是：

- 人在什么节点介入
- 介入时看什么
- 介入后如何让系统继续自动往下走

换句话说，好的 harness 不是取消人工，而是把人工安排到最有价值的位置上。

## 一个容易理解的例子

假设你要做一条内容生产流水线。

如果你只会写 prompt，你可能每一步都要重新说：

- 帮我整理策划
- 帮我生成海报文案
- 帮我转写音频
- 帮我做播客文案
- 帮我整理发布素材

这样每一步都像单独求助一次。

但如果你用 `harness engineering` 的方式来搭系统，你会这样设计：

- 固定策划模板
- 固定目录与文件命名
- 固定转写工具
- 固定摘要模板
- 固定播客文案输出格式
- 固定发布物料检查表
- 固定人工审核节点

这样一来，AI 不再是在做五个互相割裂的小任务，而是在跑一条可复用的工作流。

这就是从“会聊天”到“会工作”的差别。

## 怎样开始实践

如果你已经会写 prompt，下一步可以按下面这个顺序升级。

### 第一步：先整理环境


先问自己几个问题：

- 我的文件和目录是不是清楚
- AI 能不能稳定找到输入和输出
- 不同任务有没有固定命名规则
- 同类资料是不是放在同一位置

### 第二步：沉淀可复用工具

找出最常重复做的任务，把它们变成固定模块：

- 转写
- 总结
- 研究
- 评审
- 报告输出
- 自动验证


### 第三步：写清楚验收标准

不要只说“帮我做一个研究报告”，而要说清楚：

- 数据来源要求
- 时间范围要求
- 交叉验证要求
- 输出结构要求
- 哪些情况必须打回重做

### 第四步：把过程落盘

复杂任务一定要有过程记录，不要把所有状态都放在聊天上下文里。

可以记录：

- 当前阶段
- 已完成步骤
- 下一步计划
- 失败原因
- 中间产物路径

### 第五步：定义人工介入点

想清楚哪些步骤可以自动放行，哪些必须人工确认。

例如：

- 对外发布前必须人工审核
- 涉及成本支出前必须人工确认
- 涉及敏感数据前必须人工审批

这会让你的系统既自动化，又可控。

## 常见误区

### 误区一：把 Harness 理解成更复杂的 Prompt

Harness 不是 prompt 的加强版，而是任务运行框架。

### 误区二：一上来就追求全自动

全自动不是起点，稳定才是起点。

很多流程先做到“80% 自动 + 20% 人工关键审核”，往往比盲目追求 100% 自动更可靠。

### 误区三：一开始就铺很多 Agent

如果职责边界、工具权限、回退机制都没设计好，多 agent 只会把错误放大得更快。

### 误区四：只关注模型，不关注系统

模型能力当然重要，但在很多真实任务里，真正决定结果质量的，往往是环境、流程、标准和记录。

## 最后的理解

你可以把 AI 的进化过程理解成这样：

- `prompt engineering` 让 AI 更会回答
- `context engineering` 让 AI 更懂材料
- `harness engineering` 让 AI 更能工作

这也是为什么今天真正有价值的 AI 应用，越来越像一套系统，而不只是一个聊天框。

当你开始关心目录结构、工具链、验收标准、过程记录、人工介入和多 agent 协作时，你其实已经不只是“在用模型”，而是在做 AI 的工程化设计。

而这，正是 `harness engineering` 的核心意义。
