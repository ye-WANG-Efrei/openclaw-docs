在我们讨论 AI 助手的安全问题之前，先把 OpenClaw 的设计理念说清楚——它的安全性建立在两个核心原则上：

- **本地优先**：能在本地处理的，不送上公网
- **显式授权**：任何新的访问，都需要你主动批准

理解了这两点，后面所有的安全配置都会显得非常自然。

---

## 一、通讯渠道的 DM 安全策略

OpenClaw 常接入飞书、微信、Telegram 等通讯工具。这意味着一个问题：**如何防止陌生人随意调用你的 AI 助手，以及背后的 Token 余额？**

OpenClaw 提供了四种 DM 安全策略，务必理解每种模式的含义：

| 策略 | 说明 | 建议 |
| --- | --- | --- |
| `pairing` | 未知发送者需先获取配对码，经你手动授权后才能对话 | ✅ 默认推荐，最安全 |
| `allowlist` | 仅允许配置文件中预设的白名单联系人 | ✅ 适合已知联系人场景 |
| `open` | 允许所有入站消息直接访问 AI | ❌ 严禁在未保护情况下使用 |
| `disabled` | 忽略所有 DM | 适合仅群组使用的场景 |

**重点讲一下 `pairing` 模式的工作方式：**

当一个陌生人向你的机器人发消息时，他会收到一个配对码，而不是直接和 AI 对话。此时你需要在运行 Gateway 的终端上手动执行：

```bash
openclaw pair <code>
```

只有你执行了这条命令，对方才能正式开始对话。

> **关于 `open` 模式：强烈建议永远不要在未经保护的情况下启用它。** 一旦开放，任何人都可以直接调用你的 AI，轻则 Token 被盗刷，重则隐私泄露。

**配置示例：**

```json
{
  "channels": {
    "telegram": {
      "enabled": true,
      "botToken": "your-bot-token",
      "dmPolicy": "pairing",
      "allowFrom": ["tg:123456789"]
    }
  }
}
```

## 二、敏感信息的隔离管理

OpenClaw 的 Workspace 文件加载机制本身就提供了数据隐私的分层保护，关键在于你要知道哪些文件在什么时候会被加载。

### MEMORY.md 的特殊地位

在所有 Workspace 文件中，`MEMORY.md` 有一个其他文件没有的特性：

> **`MEMORY.md` 仅在主会话（Main Session）中加载，不会在子智能体或普通会话中被调用。**

这意味着你可以把安全敏感的长期记忆放在这里，大大降低隐私信息被子 Agent 误读或泄露的风险。

### API Key 的正确存放方式

不要把 API Key 直接写进 `openclaw.json`。如果这个文件不慎被分享，密钥就直接暴露了。

正确做法是存入系统环境变量，再在配置里引用：

```json
{
  "skills": {
    "entries": {
      "my-skill": {
        "apiKey": {
          "source": "env",
          "id": "MY_API_KEY"
        }
      }
    }
  }
}
```

对应的环境变量设置：

```bash
# macOS / Linux
export MY_API_KEY="sk-..."

# Windows PowerShell
$env:MY_API_KEY = "sk-..."
```

## 三、代码与执行环境安全

当 AI 需要执行代码或调用复杂 Skill 时，执行环境的安全就非常重要了。OpenClaw 提供了两种保护手段。

### 沙盒执行（Sandbox）

沙盒模式可以把 Agent 的执行操作限制在隔离环境中，防止错误或恶意指令对宿主机造成破坏：

```json
{
  "agents": {
    "defaults": {
      "sandbox": {
        "mode": "non-main",
        "scope": "agent"
      }
    }
  }
}
```

对于执行代码、调用脚本类的 Skill，**建议默认开启沙盒**。

### 本地模型：安全等级最高的方案

通过 [Ollama](https://ollama.com) 部署本地模型（如 Qwen、GLM 等），是目前安全等级最高的使用方式：

- **数据不经过公网**，所有推理都在本地服务器完成
- 适合处理机密文件、内部资料、个人隐私数据
- 同时也是前面提到的 Heartbeat 优化方案——用本地小模型承担高频巡检任务，既安全又省钱

```json
{
  "agents": {
    "defaults": {
      "model": {
        "primary": "ollama/qwen2.5:7b"
      }
    }
  }
}
```

## 四、接入飞书等平台的认证安全

在飞书进阶部署场景下，安全保障来自于整条链路的多层认证，缺一不可。

**认证链路：**

```text
飞书用户消息
  → 飞书服务器（App ID + App Secret 双向认证）
    → Cloudflare Tunnel（加密通道，避免暴露本地端口）
      → 本地 Gateway（首次私聊需 pair 授权）
        → OpenClaw Agent
```

**每一层的作用：**

1. **App Credentials**：通过飞书官方的 App ID 和 App Secret 进行双向认证，确保只有合法的飞书应用才能触发回调
2. **Cloudflare Tunnel**：流量通过加密通道传输，避免了直接开放路由器端口带来的端口扫描和攻击风险
3. **首次授权确认**：即使公网链路完全打通，机器人在首次私聊时仍会提示"未配置访问权限"，必须通过 `pair` 命令手动完成本地授权才能使用

## 五、常见风险速查

| 风险 | 可能后果 | 缓解方式 |
| --- | --- | --- |
| DM 策略设为 `open` | Token 被盗刷、隐私泄露 | 始终使用 `pairing` 或 `allowlist` |
| API Key 明文写入配置文件 | 密钥随文件泄露 | 改用环境变量注入 |
| 未开启沙盒执行 | 恶意脚本破坏宿主机 | 默认开启 `sandbox` |
| 敏感记忆存入普通 Workspace 文件 | 子 Agent 误读隐私 | 敏感内容放入 `MEMORY.md` |
| Gateway 直接暴露公网端口 | 遭受端口扫描与攻击 | 使用 Cloudflare Tunnel 做内网穿透 |
| 第三方 Skill 未经审查 | 恶意代码执行 | 安装前通读 `SKILL.md` 和 `scripts/` |
| Prompt 注入 | 外部内容诱导模型执行危险操作 | 不可信输入与系统指令分层处理 |

## 六、三大安全支柱

最后，用三条原则来总结 OpenClaw 安全运行的核心：

1. **始终保持 `dmPolicy: "pairing"`** — 让每一次新的访问都经过你的显式授权
2. **长期记忆存入 `MEMORY.md`** — 利用系统的加载隔离机制保护隐私数据
3. **机密任务优先使用本地模型** — 数据不出本地，才是真正的安全

做到这三点，OpenClaw 的安全边界就基本稳固了。
