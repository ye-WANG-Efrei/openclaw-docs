## 系统流转

```text
User -> Agent -> Model -> Tools -> Skills -> Memory
```

这不是一张装饰图，而是一条真正值得治理的工程链路。每一层都有不同的职责、风险和优化方法。

## 组件拆解

| 组件 | 主要职责 | 输入 | 输出 | 常见失效方式 |
| --- | --- | --- | --- | --- |
| User | 定义目标与约束 | 任务、背景、边界 | 请求 | 目标模糊 |
| Agent | 规划与编排 | 请求、策略、Skill | 模型调用与工具调用 | 任务拆解差 |
| Model | 推理、生成、总结 | prompt、上下文 | 文本或结构化结果 | 能力不匹配 |
| Tools | 与外部系统交互 | 参数与权限 | 数据或副作用 | 权限误用 |
| Skills | 提供过程知识 | 工作流、参考资料 | 更稳定的执行路径 | 指令过时或过宽 |
| Memory | 保存值得复用的上下文 | 摘要、状态、事实 | 后续可检索上下文 | 噪声污染或泄露 |

## 请求生命周期

1. 用户请求进入系统，并带上目标与约束。
2. Agent 选择或继承合适的模型档位。
3. 相关 Skill 被加载，提供领域过程知识。
4. 模型判断是否需要工具。
5. 工具结果再回流到推理链路中。
6. 仅把真正有长期价值的信息写入记忆。

## 设计原则

- 模型选择必须足够明确，便于审计与回溯
- 工具是“能力边界”，不是中性附属品
- Skill 要小而专注，便于复用和维护
- 记忆只保存未来确实会带来价值的内容

## 需要重点盯的失效点

- 小任务却总是命中高成本模型
- Skill 太模糊，导致模型每次重新摸索流程
- 工具权限比任务需要大得多
- 记忆保存了过时或带偏见的摘要
