## 为什么要加 Gateway

如果应用直接散落着对多个模型提供方的调用，后续做治理会很痛苦。Gateway 的价值就在于把模型流量统一收口：路由策略、限流、日志、回退和成本治理都能在一个位置完成。

## Gateway 常见职责

| 职责 | 为什么重要 |
| --- | --- |
| 模型路由 | 让不同任务走不同提供方或模型档位 |
| 策略控制 | 拦住不安全或不合规的调用 |
| 成本治理 | 控制高成本路径的使用量 |
| 审计日志 | 解释最终用了什么模型、为什么 |
| 重试与回退 | 降低单一提供方失败带来的影响 |

## 参考拓扑

```text
Client -> OpenClaw app -> Gateway -> Provider API or local model runtime
```

## 起步配置

```env
OPENCLAW_GATEWAY_URL=https://gateway.example.com
OPENCLAW_GATEWAY_TOKEN=<service-token>
OPENCLAW_GATEWAY_TIMEOUT_MS=30000
```

## 运维检查点

- 是否记录最终提供方与模型
- 是否暴露请求 ID 便于追踪
- 是否把开发和生产网关凭证分离
- 提供方失败时有没有清晰回退行为

## 常见错误

- 把路由规则藏在应用代码里，而不是 Gateway 层
- Gateway 无法判定时仍然“失败开放”
- 所有环境共用一组网关 token
